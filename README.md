# PowerScanner

PowerScanner is a standalone Windows malware scanner written in Rust
with a native egui desktop dashboard, SHA-256 blacklist detection, YARA-X rule
matching, encrypted signatures, and tamper-evident scan results.

> Current status: Phase 1 core, GUI, encrypted signature loading, signed result
> persistence, reproducible rule generation, and sealed release packaging are
> implemented. Updater work remains future work.

## Phase 1 scope

Phase 1 targets an on-demand Windows x64 scanner with:

- Native desktop GUI built with `eframe`/`egui`.
- Three scan presets: Quick, Full, and Risky Spots.
- SHA-256 exact-match blacklist checks.
- YARA-X rule compilation and scanning.
- Core incremental cache support using file size and modification time (GUI
  persistence/integration is deferred).
- First-run signature import from `signatures/`, then encrypted at rest.
- HMAC-signed append-only JSONL results under `%ProgramData%\PowerScanner`.

Phase 1 does not include real-time monitoring, process or memory scanning,
registry inspection, quarantine/delete actions, server sync, SQLite storage,
fuzzy hashing, or behavior detection.

The Rust workspace layout is:

```text
.
|-- core/         # UI-agnostic scan, crypto, signatures, and result sink logic
`-- gui/          # eframe/egui desktop app
```

`core` must not depend on GUI crates, so the scan engine can later be reused by
a CLI, Windows service, or backend-connected agent.

## Run

The GUI resolves signatures next to the executable. To build a validated
Defender-safe release, run the packaging script:

```powershell
pwsh tools/package-release.ps1
./release/powerscanner.exe
```

The script verifies the encrypted bundle, provenance hash, attribution files,
licenses, and absence of plaintext rules before staging the executable.

## Scan presets

| Preset | Scope | Phase 1 behavior |
|--------|-------|------------------|
| Quick | High-risk user and system locations | Same roots as Risky Spots in Phase 1; process-path scanning is deferred |
| Full | Existing `A:\` through `Z:\` drive-letter roots (fixed, removable, or mounted) | Broadest drive-letter scan; volumes without a drive letter are not enumerated |
| Risky Spots | Temp, AppData, Downloads, Startup, System32, and Windows Temp | Focuses on common malware drop and persistence locations |

The GUI is designed to show a circular progress ring, live scanned-file stream,
Scanned/Malicious/Elapsed metrics, and a filterable results table after a scan
finishes.

## Signatures

The repository includes a bundled signature set under [`signatures/`](signatures):

```text
signatures/
|-- hashes.txt                 # development input, not release output
|-- MANIFEST.json
|-- NOTICE.md
|-- bundle.psenc        # pre-sealed release bundle
|-- licenses/
`-- rules/
    `-- bundled.yar      # generated build intermediate (git-ignored)
```

The bundled YARA set is regenerated by `tools/build-rules.sh` from pinned
ReversingLabs, Yara-Rules, and bartblaze sources, then sealed by
`tools/seal-bundle`. Plaintext rules are build intermediates and are not part of
a release. See
[`signatures/NOTICE.md`](signatures/NOTICE.md) for attribution and GPL-2.0
obligations that apply to the bundled rule set.

Custom signatures use the same source layout:

- `hashes.txt` contains one SHA-256 hash per line. Blank lines and comments are
  ignored.
- `rules/*.yar` contains YARA source rules.
- After first import, the app seals signatures into an encrypted bundle. The
  bundle key is portable and app-embedded so a shipped bundle works on any
  machine; this is obfuscation-grade extraction resistance, not a secret trust
  anchor.

## Results

Phase 1 stores signed, append-only JSONL results in:

```text
%ProgramData%\PowerScanner\results\
```

Each result line is HMAC-SHA256 signed. Verification detects edits to surviving
lines or forged result lines that do not have a valid machine-derived signature.
Per-line signatures do not prove that complete lines were not deleted. Because
the machine identifiers are locally readable, this is a tamper-evidence
mechanism for offline/manual changes, not a defense against malware already
running with local access.

## Security model and limitations

PowerScanner uses authenticated encryption or authenticated signatures for
persisted security-sensitive files.

- Signature bundles are encrypted at rest with AES-256-GCM using a portable
  Argon2id-derived key from an app-embedded secret. Releases ship only the
  sealed bundle; plaintext YARA sources are build inputs and the embedded key is
  intentionally documented as obfuscation, not a real secret.
- Result lines are signed with HMAC-SHA256 using a separate machine-derived key.
- Auth failures are treated as tamper evidence, not silently ignored.
- Result-signing keys are machine-derived; the portable bundle key is an
  explicit, documented exception and is not treated as a trust anchor.

Important limitations:

- Endpoint-side rule encryption raises the cost of extracting rules, but it
  cannot make extraction impossible on a machine the attacker controls. The app
  must decrypt rules in memory to scan with them.
- Result signing makes offline/manual tampering detectable, not preventable.
  Malware with local access can read the machine identifiers and reproduce the
  current derivation, so Phase 1 does not claim to stop active local forgery.
